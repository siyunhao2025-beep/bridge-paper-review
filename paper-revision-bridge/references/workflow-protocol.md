## 1. 启动确认门

在任何论文读取、目录创建、审稿派发、修改或定时任务安装之前，先取得一份用户确认清单。清单至少包含：论文绝对路径、权威可编辑源、协作目录位置许可、全部 AI 名称/产品/版本、主力、秘书、目标期刊、稿件类型、语言、五审实现方式、监测是否启用、轮询间隔、时区、持续期限、运行宿主、系统定时任务授权、唤醒适配器以及无适配器时的降级方式。

用户必须在看到整理后的清单后明确回复“确认开始”或同义的无歧义授权。脚本用 `--intake-confirmed yes` 记录这个门槛，但命令行标志不能替代真实用户确认。

## 2. 角色所有权

| 角色 | 唯一责任 | 禁止事项 |
|---|---|---|
| 用户 | 选择主力/秘书、权威源、期刊；裁决证据不足与审稿冲突 | 被模型替代作学术真实性决定 |
| 秘书 | 建档、组织五审、合并意见、维护状态、判定硬门槛、生成可复制给主力的 Markdown | 代主力偷偷改稿；删减不同意见以抬高分数；只在聊天中口头交接 |
| 主力 | 按问题 ID 修改源稿、生成渲染件、变更日志和可复制给秘书的 Markdown | 修改评分；把未解决项标成已解决；只说“已完成”而不交文件证据 |
| 五位审稿人 | 独立阅读、证据定位、评分、复核旧问题 | 互相复制结论；编造引用或实验 |

若一个模型模拟五审，必须在 `00_协作配置.md` 中写明“单模型五次隔离审阅”，不能称为五个独立智能体。

## 4. 状态机

```text
awaiting_review
  ├─ 秘书输出 ready 交接且通过全部硬门槛 ─> complete
  ├─ 秘书输出阻断交接；缺证据/冲突/停滞 ─> attention_required
  └─ 秘书输出 revise 交接 ───────────────> awaiting_revision

awaiting_revision
  └─ 主力生成含可复制区的 Markdown ─────> awaiting_review（下一轮）

attention_required
  └─ 用户提供决定或证据 ───────────> awaiting_revision
```

有效阶段只有 `awaiting_review`、`awaiting_revision`、`attention_required`、`complete`。每次状态变化必须原子写入 `bridge-state.json`，同步刷新 `00_当前状态.md`，并向 `events.jsonl` 追加单调递增事件。`record-review` 和 `lead-done/accept-marker` 必须先完成对应 Markdown 的结构、路径与散列校验，才能改变阶段。

## 5. 交付物契约

### 审稿报告

每份报告必须包含以下标题：

- `## 摘要结论`
- `## 硬伤与矛盾`
- `## 逐项审稿意见`
- `## 防御性写作审查`
- `## 上轮问题复核`
- `## 评分`
- `## 投稿建议`

每条问题给出唯一 ID、位置、证据/推理、风险、可执行修改和验收条件。第二轮起沿用旧 ID；同一问题不得换 ID 伪装成新问题。

### 汇总与任务单

`审稿汇总_RNN.md` 必须记录五审共识、分歧、各自分数、硬伤、旧问题状态和秘书结论。`修改任务单_RNN.md` 必须把所有 P0/P1 收入；P2/P3 可说明不采纳理由，但不能静默删除。

### 秘书→主力 Markdown

`<秘书>_<N>审<论文名>_给<主力>.md` 由 `record-review --agent <秘书>` 强制生成，必须包含：

- 工作流 ID、发送者、接收者、轮次、生成时间和 `ready/revise/attention_required`；
- `## 可直接复制给主力的话`；
- 当前已审论文的绝对路径、大小和 SHA-256；
- 五位审稿人的逐人总分、最低维度、开放问题和门槛失败原因；
- `审稿汇总_RNN.md` 与 `修改任务单_RNN.md` 的路径、SHA-256 和全文；
- 主力回交文件名与内容要求；若已通过，则明确停止自动改写和“非录用保证”。

缺少该文件时，`awaiting_review` 不得进入 `awaiting_revision`、`attention_required` 或 `complete`。秘书必须实际读取当前论文；仅阅读主力上一份交接文件不算复审。

### 主力→秘书 Markdown

`<主力>_<N>修<论文名>.md` 必须包含：

- 主力名称、轮次和生成时间；
- 接收秘书及 `## 可直接复制给秘书的话`；
- 修改后文件的绝对路径、大小和 SHA-256；
- 变更日志正文或路径；
- 已解决问题 ID；
- 未解决问题 ID及理由；
- 编译、导出、引用、公式、图表和交叉引用检查结果。

完成标记不能代替修改后的论文。秘书复审时必须打开标记中列出的当前稿件。可复制区必须要求秘书沿用旧问题 ID、检查新矛盾与防御性写作，并在复审后输出下一份秘书→主力 Markdown。

主力能运行桥接脚本时使用 `lead-done` 原子生成交接并推进状态。外部主力若自行写入交接，定时 `scan` 只产生检测事件，不自动信任内容；`accept-marker` 必须验证必需标题、工作流 ID、双方身份、修改稿和变更日志路径及其 SHA-256，任何缺项都拒绝推进。

### 最终报告

`最终可投稿报告.md` 必须列出目标期刊、最终文件散列值、各审稿人分数、通过的硬门槛、仍需作者承担的残余风险，并声明“非录用保证”。

## 6. 自动唤醒适配器

Skill 本身不拥有外部产品的唤醒权限。定时扫描和唤醒 AI 是两个不同能力：`scan` 可以发现预期完成标记并生成幂等事件，但真实自动化仍需要宿主调度器与产品侧适配器执行：

1. 每隔用户确认的时间调用 `bridge.py scan`；交互式宿主也可调用最多 60 秒的 `wait`。
2. 读取比自身游标大的 `event_id`；以事件 ID 做幂等键，避免重复派单。
3. 对 `review_requested` 唤醒秘书并传递主力→秘书 `handoff`；对 `revision_requested` 唤醒主力并传递秘书→主力 `handoff`；对 `attention_required` 通知用户并附秘书交接；对 `workflow_completed` 传递最终秘书确认后停止轮询。
4. 只向智能体传递协作目录、交接 Markdown 路径和事件元数据，让智能体自行读取文件；不要把论文内容拼成 shell 命令。
5. 成功派单后由适配器保存自己的游标。禁止把“看到文件”当作“派单成功”。

Workbuddy、GPT 或其他产品若没有文件事件/API，只能使用人工交接：打开事件指向的 Markdown，复制其中“可直接复制给主力/秘书的话”，再附上协作目录路径。接入任何具体产品前，先查验其当前官方接口，不猜测命令名或权限。

监测状态必须分级：

- `configured`：参数已保存，调度器未验证。
- `active`：调度器能调用 `scan`，但不代表 AI 已被唤醒。
- `wake_verified`：真实测试已证明适配器能唤醒目标 AI、传递工作区和事件 ID，并避免重复派单。
- `manual`：用户明确选择人工检查。

安装系统定时任务属于持久化外部更改，只能在用户明确授权后执行。记录任务名称/ID、间隔、时区和宿主；提供状态检查与卸载路径。

## 7. 失败与恢复

- 协作目录已存在：运行 `status` 和 `verify`；不要再次 `init`。
- 状态锁存在：确认没有另一进程正在写；不要直接删除仍在使用的锁。
- PDF-only：保持审稿可用，但把修改任务标成阻断，直到获得可编辑源或用户批准转换。
- 编译失败或 DOCX/PDF 不一致：不得进入复审，先修复渲染链。
- 双向交接缺失、缺必需标题、缺文件散列或登记后被改动：`verify` 失败；回到生成方重建可信交接，不得手工跳阶段。
- 新实验、数据、伦理审批或作者判断缺失：进入 `attention_required`，不得编造补齐。
- 审稿人结论冲突：秘书保留双方证据，让用户裁决，不能用平均分消除冲突。
- 连续两轮总分平均提升小于 0.2，或第五轮仍失败：暂停循环并诊断是证据上限、任务定义还是期刊不匹配。
- 状态文件损坏：先备份整个协作目录，再根据 `events.jsonl` 和交付物重建；禁止猜测已解决项。
