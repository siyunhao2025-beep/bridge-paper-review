# 五审角色与严格评分规则

## 五位审稿角色

在读完标题、摘要、关键词、全文和补充材料后，根据领域动态补全每位审稿人的专业画像，但保持职责不变。

| ID | 核心职责 | 必查内容 |
|---|---|---|
| R1 | 领域、问题价值与创新性 | 研究问题、贡献边界、相关工作、期刊范围、过度新颖性声明 |
| R2 | 方法、统计与可复现性 | 设计、样本、对照、假设、统计、消融、敏感性、代码/数据可得性 |
| R3 | 证据链与内部一致性 | 结论是否被结果支持；正文、表、图、公式、摘要、结论的数字与方向一致性 |
| R4 | 期刊适配、结构与呈现 | 稿件类型、篇章逻辑、图表可读性、格式、引文覆盖、读者定位 |
| R5 | 学术表达、完整性与质疑压力测试 | 术语、可读性、研究完整性、伦理/披露、最强反例、防御性写作 |

五位审稿人都必须检查防御性写作；R5 只是承担主责，不代表其他人可以跳过。

## 问题分级

- `P0 硬伤`：方法或统计无效、数据矛盾、结论不成立、伦理/完整性风险、关键结果不可核验、严重期刊错配。
- `P1 必改`：不修会显著影响正确性、可复现性、可理解性或编辑决定。
- `P2 应改`：明显改善论证、结构或表达，但不单独阻止投稿。
- `P3 可选`：偏好性建议。不得用 P3 数量压低总分。

每条问题必须写成：`ID → 精确位置 → 原文/事实（短引或转述）→ 为什么是问题 → 修改动作 → 验收条件`。无法直接核验的引用或事实标记为 `[需检索验证]`。

## 防御性写作审查

把以下模式视为待检查对象，而不是自动删除词表：

- 用“不可避免的局限”“受条件所限”等措辞预先为可修问题辩护。
- 在正文中与假想审稿人争辩，或堆砌理由证明一个常规选择“合理”。
- 先提出超出证据的强结论，再用大量保留句兜底。
- 用 `novel`、`first`、`robust`、`comprehensive`、`significant` 等自我评价代替证据。
- 反复强调局限以降低读者期待，导致贡献和适用边界都不清楚。
- 用模糊主语、被动语态或名词化隐藏责任、数据来源或失败条件。
- 对没有执行的实验、分析或比较给出解释，却不明确标注为未来工作。

不要误伤以下必要内容：统计不确定性、真实局限、适用范围、替代解释、负结果和伦理边界。推荐修法是“给出证据 → 明确边界 → 直接说明剩余不确定性”，不是把所有谨慎措辞改成绝对断言。

每位审稿人都必须至少回答：

1. 是否存在防御性措辞？列出位置和功能。
2. 它是在校准不确定性，还是在回避可修的证据/方法问题？
3. 应删除、改写、补证据，还是保留？
4. 修改后是否造成过度自信或新的事实外推？

## 评分维度

每位审稿人分别给出以下 0–10 分，不允许只给总分：

- `novelty_significance`：问题价值、贡献与边界。
- `methods_rigor`：设计、统计、复现与方法适配。
- `evidence_consistency`：证据链、数字和跨章节一致性。
- `clarity_journal_fit`：结构、呈现和目标期刊适配。
- `defensive_writing`：直接、证据约束、不过度辩护且保留必要不确定性。
- `overall`：不能高于明显短板可以合理支撑的水平。

参考锚点：

- `9.0–10`：无 P0/P1；仅有局部 P2/P3；可直接投稿或做极小修订。
- `8.0–8.9`：主体可靠，但至少有一项实质性修改。
- `6.0–7.9`：存在多项重大问题，需大修。
- `<6.0`：核心设计、证据或定位不足，当前版本不宜投稿。

## 通过门槛

必须同时满足：

1. 五位审稿人的 `overall >= 9.0`。
2. 五个维度对每位审稿人均 `>= 8.5`。
3. 五位审稿人均 `submission_ready=true`。
4. 所有 `blocking_issue_ids`、`must_fix_issue_ids`、`unresolved_prior_issue_ids`、`recurring_issue_ids` 为空。
5. `journal_compliance=true` 且 `source_integrity_checked=true`。
6. `conflicts_needing_user` 和 `missing_evidence_actions` 为空。

平均分仅用于观察进展，永远不能替代上述逐人硬门槛。

## scorecard 约束

`scorecard_RNN.json` 必须保留脚本生成的键。每位审稿人填写五个维度、总分、是否可投稿、P0/P1 ID。秘书填写期刊/源文件检查、旧问题、冲突、缺证据行动和最终建议。

建议必须是 `revise`、`attention_required` 或 `ready` 之一。即使秘书写 `ready`，脚本仍按硬门槛独立计算，不接受自报通过。
